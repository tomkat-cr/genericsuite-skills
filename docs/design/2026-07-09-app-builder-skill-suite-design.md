# GenericSuite App-Builder Skill Suite — Design

**Date:** 2026-07-09
**Repo:** `packages/genericsuite-skills`
**Related tickets:** GS-254 (app generation skills — primary), GS-306 (new
project from templates)

## Goal

A set of Claude Skills that lets a developer build an entire GenericSuite
full-stack app — starter project, JSON configs, backend code, frontend code,
and AI features — either skill-by-skill or through a single guided
orchestrator flow.

Per GS-254, the initiative is complete only when the skills are verified
working, added to the GenericSuite Skills repository, and **published to the
Claude Skills marketplace and skills.sh**.

## Decisions (agreed 2026-07-09)

1. **Architecture:** specialized skills + one orchestrator (`gs-app-builder`).
   Every specialized skill remains usable standalone.
2. **Reference material:** each skill bundles a curated `references/`
   directory (distilled patterns + code templates extracted from
   genericsuite-basecamp), regenerated by a sync script so they don't drift.
3. **App starter:** one `app-starter` skill wrapping
   `genericsuite-basecamp/scripts/new-project-from-template.sh`
   (fastapitemplate covers frontend + backend + MCP server). ExampleApp
   variant with backend-framework choice comes later (GS-306).
4. **Backend code generation:** write business logic against the
   genericsuite-be abstraction layer; FastAPI router wiring is the default
   output. Flask/Chalice wiring can be added later without changing the
   business-logic templates.

### New skills

#### 1. `python-fastapi-code-builder`

Generates custom (non-generic) backend endpoints and business logic.

- **Inputs:** entity/feature description, backend JSON configs if the
  feature extends a CRUD entity, external API details if wrapping one.
- **Outputs:**
  - `lib/models/<domain>/<feature>.py` — business logic returning the
    standard `{"error", "error_message", "resultset"}` shape, using
    `GenericDbHelper` / DbAbstractor-safe (MongoDB-syntax) queries.
  - `lib/routers/<feature>.py` — FastAPI router following the
    fastapitemplate/exampleapp router idiom (JWT-aware `request`
    handling, `Config`, `CommonAppContext`).
  - Wiring snippet for `lib/main.py` router registration and/or
    `endpoints.json` when the endpoint is generic-handler based.
- **Canonical patterns (source of references/):**
  `exampleapp/apps/api-fastapi/lib/routers/fda_food_endpoint.py`,
  `lib/models/external_apis/*`, `lib/models/admin_food/*`,
  fastapitemplate `server/lib/*`.

#### 2. `python-ai-code-builder`

Wires the GenericSuite AI assistant into a backend.

- **Outputs:** `lib/routers/ai_assistant.py` (or verification that the
  template one is intact), AI config env vars checklist
  (`OPENAI_API_KEY`, model selection, storage bucket vars), registration
  in `lib/main.py`, chatbot menu/endpoint JSON entries.
- **Canonical patterns:** fastapitemplate `server/lib/routers/ai_assistant.py`,
  exampleapp equivalent, `genericsuite-be-ai` docs
  (Backend-Development/GenericSuite-AI).

#### 3. `python-ai-tools-code-builder`

Generates LangChain tools (GPT functions) callable by the AI assistant.

- **Inputs:** tool purpose, parameters, which model/endpoint or external
  API it calls.
- **Outputs:**
  - `lib/models/ai_chatbot/ai_gpt_fn_<domain>.py` — `@tool` functions with
    Pydantic param schemas, `interpret_tool_params`, `CommonAppContext`
    (`cac`) pattern, `gpt_func_error` error handling, optional
    `lang_translate` support.
  - Registration edits for `lib/models/ai_chatbot/ai_gpt_fn_index.py`
    (imports, `cac` propagation, functions dict).
- **Security rules baked in:** wrap AI-generated URLs/paths with
  `is_safe_url()` / `is_safe_local_path()`; never log unsanitized input.
- **Canonical patterns:** exampleapp `ai_gpt_fn_fda.py`, `ai_gpt_fn_app.py`,
  `ai_gpt_fn_index.py`.

#### 4. `jsx-ai-code-builder`

Adds AI features to the React frontend.

- **Outputs:**
  - `chatbot_popup` / `aux_component: ChatBotButton` additions to frontend
    JSON configs (delegating JSON edits to config-builder conventions).
  - `genericsuite-ai` imports and registry entries in existing components
    (the `gsAi.ChatBotButton` idiom from `UserIngredients.jsx`).
  - AI assistant page/menu wiring in `App.jsx` and `app_main_menu.json`.
- **Constraints:** reuse `renderMarkdownContent()`; never
  `dangerouslySetInnerHTML`.
- **Canonical patterns:** exampleapp `apps/ui/src/components/UsersMenu/*.jsx`,
  `App.jsx`, genericsuite-fe-ai docs.

#### 5. `menu-builder`

Creates or updates the app menu in `backend/app_main_menu.json`. Today
`config-builder`/`jsx-code-builder` only print menu snippets and leave the
edit to the user; this skill applies them.

- **Inputs:** component/EditorData names (from config-builder or
  jsx-code-builder output, or user-described), menu group title and
  `location` (`top_menu` / `side_menu`), `sec_group` per entry.
- **Outputs:** idempotent merge into `backend/app_main_menu.json` — adds
  `editor` entries into an existing `nav_dropdown` group's
  `sub_menu_options` or creates the group; never duplicates an existing
  `element`; preserves ordering and unrelated entries.
- **Rules:** only master components get menu entries (children are reached
  through the parent form); validate against the menu structure in the
  Configuration Guide docs.
- **Canonical patterns:** exampleapp/fastapitemplate
  `config_dbdef/backend/app_main_menu.json`, Configuration Guide
  (App-Menu-and-API-endpoints documentation).

#### 6. `endpoints-builder`

Creates or updates API endpoint registrations in
`backend/endpoints.json` (same rationale: today only snippets are printed).

- **Inputs:** entity backend/frontend JSON configs (to derive
  `json_file`, URL, methods), or a custom router description when the
  endpoint is not GenericEndpointHelper-based.
- **Outputs:** idempotent merge into `backend/endpoints.json` —
  `GenericEndpointHelper` route blocks for CRUD entities; skips child
  entities with `subType: "array"` (data lives in the parent document);
  adds entries for `subType: "table"` children; never duplicates a
  `url_prefix`.
- **Canonical patterns:** exampleapp/fastapitemplate
  `config_dbdef/backend/endpoints.json`, the endpoint snippet patterns in
  config-builder Step 3 / jsx-code-builder Step 4c.

#### 7. `mcp-builder`

Builds the project's MCP server from the AI tools generated by
`python-ai-tools-code-builder` and from registered API endpoints.

- **Inputs:** the `lib/models/ai_chatbot/ai_gpt_fn_*.py` modules (their
  `*_func` plain-function variants are the wrapping targets — this is why
  every LangChain `@tool` gets a `_func` companion), plus `endpoints.json` /
  backend configs for CRUD entities worth exposing as MCP tools.
- **Outputs:**
  - `mcp-server/mcp_server.py` — FastMCP server via
    `genericsuite.mcplib.util.create_app`, with `@mcp.tool()` wrappers
    delegating to each `*_func`, standard auth tools
    (`mcp_authenticate`, `get_api_keys`), `verify_app_context` +
    `tool_result` result handling, and `cac` object propagation from every
    imported tool module.
  - Optional `@mcp.tool()` wrappers for generic CRUD endpoints
    (list/get/create/update/delete per selected entity) and
    `@mcp.prompt()` entries when the tool modules export prompt functions.
  - `mcp-server/` scaffolding when missing: `pyproject.toml`/`package.json`,
    client config files (`claude_desktop_{stdio,http}_config.json`,
    `vscode_mcp_{stdio,http}_config.json`), README run instructions.
- **Canonical patterns:** exampleapp `apps/mcp-server/mcp_server.py`
  (full wrapper set incl. prompts), fastapitemplate `server/lib/mcp_server.py`
  (minimal starter) and `mcp-server/` client configs, `genericsuite-be`
  `mcplib/` utilities.
- **Dependency:** runs after `python-ai-tools-code-builder`; re-runnable to
  add wrappers for newly generated tools (idempotent edits to an existing
  `mcp_server.py`).

#### 8. `app-starter`

Bootstraps a new project. GS-254 lists a backend app starter and a frontend
app starter as separate items; this single skill covers both, because the
fastapitemplate monorepo it copies contains the frontend (`ui/`), backend
(`server/`), and MCP server in one project — no separate frontend starter
template needs to be created.

- **Behavior:** gather target dir, app name, domain, template; run
  `new-project-from-template.sh` (via curl or local basecamp clone);
  then guide through `make init-app-environment`, `.env` editing
  (with an interactive checklist of required vars), `make install-all`,
  `make dev`/`make run`.
- **Future (GS-306):** exampleapp template with backend framework
  selection — the skill's question flow already reserves a
  "template" question so this slots in without redesign.

#### 9. `gs-app-builder` (orchestrator)

The "build me an app" entry point.

- **Flow:**
  1. Interview: app purpose, entities and fields, relationships, AI
     features wanted (chatbot? AI tools? which?), deployment intent.
  2. `app-starter` → new project scaffold.
  3. `config-builder` per entity (master + children).
  4. `menu-builder` + `endpoints-builder` to register the new entities.
  5. `jsx-code-builder` per master config.
  6. `python-fastapi-code-builder` for any custom endpoints
     (followed by `endpoints-builder`/`menu-builder` for their wiring).
  7. If AI: `python-ai-code-builder` → `python-ai-tools-code-builder`
     → `jsx-ai-code-builder`.
  8. If MCP wanted: `mcp-builder` (wraps the generated AI tools and
     selected CRUD endpoints).
  9. Final checklist: env vars, `make dev`, smoke-test steps.
- **Checkpoints:** after each phase, show generated files and get user
  confirmation before continuing.
- **Implementation note:** the orchestrator is a SKILL.md instruction flow
  that invokes the other skills by name; it holds a shared "app brief"
  (entities, AI features) so later skills don't re-ask questions.

## Cross-Cutting: `references/` Sync

- Each skill gets `references/` with (a) distilled pattern docs written
  for this suite, and (b) verbatim exemplar files copied from basecamp.
- New script `scripts/sync_references.sh` in genericsuite-skills:
  copies the mapped exemplar files from a basecamp checkout
  (`BASECAMP_DIR` env var, defaults to the superproject sibling path)
  into each skill's `references/`, and prints a diff summary.
- Make target: `make sync-references`.
- The existing `gs_docs/` copies inside `config-builder` migrate into this
  mechanism (mapping file lists source → destination per skill).

## Repository Conventions

- Skills live under `skills/<name>/SKILL.md` with `name`, `description`,
  `argument-hint` frontmatter (match existing style).
- Register each new skill in `.claude-plugin/marketplace.json`
  (proposed plugin group: `gs-app-builder-suite`).
- Generated-output testing uses `playground/` per repo convention.
- Each skill gets `evals/evals.json` with at least 2 test cases,
  runnable through the skill-creator framework.

## Build Order (phases)

1. **Phase 0 — Foundations:** `sync_references.sh` + Make target;
   migrate config-builder/jsx-code-builder doc paths; update CLAUDE.md
   skill table and marketplace.json structure.
2. **Phase 1 — Backend core:** `menu-builder` and `endpoints-builder`
   (small, unblock the full CRUD flow end-to-end), then
   `python-fastapi-code-builder` (+ evals, playground run against a
   sample entity). Update config-builder/jsx-code-builder "next steps"
   sections to invoke the two new skills instead of printing
   apply-it-yourself snippets.
3. **Phase 2 — AI backend:** `python-ai-code-builder`, then
   `python-ai-tools-code-builder` (tools skill depends on assistant
   wiring existing), then `mcp-builder` (wraps the tools' `*_func`
   variants, so it depends on the tools skill's output conventions).
4. **Phase 3 — AI frontend:** `jsx-ai-code-builder`.
5. **Phase 4 — Starter:** `app-starter`.
6. **Phase 5 — Orchestrator:** `gs-app-builder`, exercised end-to-end in
   `playground/` building a small sample app (e.g. "invoices" domain).
7. **Phase 6 — Docs & publishing (GS-254 close-out):** README/CHANGELOG
   updates in genericsuite-skills; basecamp docs page listing the suite;
   register the suite in `.claude-plugin/marketplace.json` and publish to
   the Claude Skills marketplace and skills.sh.

Each phase is independently shippable; the orchestrator lands last
because it depends on all the specialized skills existing.

## Error Handling & Guardrails (all builder skills)

- Validate generated JSON against
  `crud_editor_config_classes.py` Pydantic models where applicable.
- Generated Python must pass Flake8; generated JSX must pass the
  project ESLint config (skills instruct running the linter and fixing).
- Backend outputs always use the standard result shape; skills refuse to
  generate code that deviates.
- Skills never write secrets; env-var placeholders only.

## Testing Strategy

- Per-skill `evals/evals.json` + skill-creator grading.
- **Evidence this works:** the `jsx-code-builder` iteration-1 benchmark
  (`jsx-code-builder-workspace/iteration-1/benchmark.json`, accepted
  2026-07-09) scored 100% pass with the skill vs. ~42% without, across
  3 eval cases (master+child, standalone, inline-select), at a cost of
  ~+8.6s / +3.7k tokens per run. The same eval pattern (assertion-based
  grading, with/without-skill comparison, `playground/` outputs) is the
  template for every new skill in this suite.
- **Lesson from iteration-1 review (2026-07-10):** structural assertions
  can pass while the output is broken at runtime — the
  `accounts-inline-select` eval used a `select_elements` array of bare
  strings (invalid per schema and broken in the GCE renderer) and still
  scored 100%. Every new skill's evals must include at least one
  runtime-validity assertion (e.g. config validates against the Pydantic
  models, generated values match the shapes the renderer/consumer actually
  reads), not just file/structure checks.
- Suite-level smoke test: orchestrator run in `playground/` producing a
  compilable sample app (backend: `python -m compileall` + import check;
  frontend: `npm run build` if feasible, else lint).

## Out of Scope (for now)

- ExampleApp-based starter with framework selection (GS-306 follow-up).
- Flask/Chalice router wiring templates (business logic is already
  framework-agnostic; wiring templates can be added later).
- Mobile (Flutter) code builder.
- CI automation of reference syncing.
